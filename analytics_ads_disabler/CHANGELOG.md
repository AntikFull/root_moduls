# Analytics & Ads Disabler — история изменений

## v7.0.1 (7001)

Исправления по итогам проверки на живых приложениях.

### Реклама пролезала мимо перехвата

Аудит на реальном приложении показал утечку: Яндекс.Реклама, перепакованная
обфускатором в короткий пакет `yads.`, не опознавалась — сигнатуры искали
`com.yandex.mobile.ads.`. Часть рекламы того же приложения при этом резалась
(необфусцированный `NativeAdView` схлопывался), поэтому со стороны выглядело
как «модуль работает через раз».

Имя класса в каждой сборке своё (`yads.zq2`, `yads.u2`), поэтому ловить можно
только по префиксу пакета. Добавлен `yads.`.

### Вердикт по стеку больше не кэшируется

Вердикт кэшировался по имени хоста. Но к одному хосту обращаются и рекламный
SDK, и собственный код приложения: к `yandex.ru` одновременно ходят
обфусцированный рекламный загрузчик и API самого приложения. Кто попадал в кэш
первым, тот и решал судьбу всех последующих запросов — либо реклама пролезала,
либо приложению обрывали его же API.

Теперь кэшируются только вердикты по спискам (они детерминированы), а вывод по
стеку вызовов считается на каждый запрос.

### Режим аудита

Новый ключ `AUDIT_LOG`. При включении в logcat попадает:

- список рекламных и аналитических SDK, найденных в приложении;
- каждый уникальный хост с вердиктом, **включая пропущенные**, и с указанием,
  чей код открыл соединение.

До этого в лог попадало только заблокированное, и разобрать жалобу «реклама
всё равно показывается» было нечем. Именно этим режимом и найдена утечка выше.

Строка `AUDIT ПРОПУСК <хост> инициатор=реклама:<класс>` прямо указывает, что
добавить в `rules.conf`.

### Прочее

- Определение Zygisk не видело ReZygisk: проверялся только модуль `zygisksu`.
- Firebase Analytics не выключался, если R8 вырезал `setAnalyticsCollectionEnabled`;
  добавлен запасной путь через настройки SDK.
- Движок впустую поднимал поток в app-zygote браузеров на Chromium.
- Повторная установка стирала пользовательский `rules.conf`; миграция v6 теперь
  одноразовая и защищена маркером.
- `minMagisk` поднят с 20400 до 24000: Zygisk появился только в Magisk 24.
- Описание модуля обещало отключение компонентов через PackageManager, которого
  в v7 нет.

## v7.0.0 (7000)

Полная переработка. Модуль перестал работать снаружи и переехал внутрь
процессов приложений.

### Что изменилось принципиально

Блокировка больше не строится на списках доменов и не требует сканирования
приложений. Zygisk загружает движок в процесс, и рекламный SDK распознаётся по
именам классов — контракту, который рекламные сети не могут ломать, потому что
на нём завязаны все приложения.

### Новый движок

* **Штатное выключение аналитики.** Движок вызывает собственный выключатель
  SDK — тот, что вендоры сделали ради GDPR: `setAnalyticsCollectionEnabled`,
  `AppsFlyerLib.stop`, `Adjust.setEnabled`, `AppMetrica.setDataSendingEnabled`
  и другие. Это дешевле блокировки сокета: трекер вообще не начинает собирать
  события, не пишет их на диск и не ставит повторные отправки. Поддержаны
  Firebase Analytics, Google Analytics, AppsFlyer, Adjust, AppMetrica,
  Yandex Metrica, Amplitude, Branch, Facebook App Events, Countly.
* **Свои правила.** `rules.conf` позволяет добавить префиксы пакетов, хосты и
  классы, которых нет во встроенных списках, а также защитить хост от
  блокировки по выводу из стека вызовов. Правила добавляются к встроенным и не
  могут снять защиту.
* **Сетевой слой.** Подмена `ProxySelector` внутри процесса. Рекламный запрос
  получает мгновенный отказ вместо таймаута, SDK штатно сообщает «нет
  заполнения», приложение работает как при отсутствии рекламы.
  Распознавание — по списку рекламных эндпоинтов и по стеку вызовов.
  Общая инфраструктура (`googleapis.com`, CDN) от эвристики защищена.
* **Схлопывание контейнеров.** Баннерные и нативные контейнеры убираются вместе
  с опустевшими обёртками, чтобы не оставалось пустой полосы. Обход дерева
  ограничен по глубине, числу узлов и частоте.
* **Полноэкранная реклама.** Interstitial, app-open и rewarded закрываются
  до отрисовки.
* **WebView.** Косметический фильтр во встроенных браузерах приложений.

Каждый слой отключается отдельно в `settings.conf`.

### Что удалено

* Индексатор рекламных поверхностей и разбор `classes*.dex` — источник
  многочасовой нагрузки на процессор и десятков гигабайт I/O.
* Парсер бинарного `AndroidManifest.xml`, написанный на awk.
* Кэш манифестов, кэш кандидатов, кэш scope пакетов.
* Сетевой фильтр на `iptables` с `-m string`: требовал `xt_string`, которого в
  прошивках обычно нет, и не покрывал QUIC.
* Отключение компонентов через PackageManager. Слой был выключен по умолчанию
  ещё в v6.1.9 из-за поломок приложений.
* Опрос конфигурации раз в 10 секунд и вызов `iptables` из этого цикла.
* Зеркалирование логов отдельным процессом, автообновление правил.

Постоянных фоновых процессов стало 1 вместо 5. Это `inotifyd`, который спит в
ядре и просыпается только при изменении настроек.

### Исправлено по итогам аудита v6.2.0

* `BLOCK_ANALYTICS` был полным no-op: категория обслуживалась только
  PM-слоем, отключённым по умолчанию. Теперь переключатель работает.
* `BLOCK_ADS` давал эффект только при наличии `xt_string` в ядре.
* Счётчик отказов в IP-режиме Ad-Killer считал успешные правила
  неудачными, из-за чего статус навсегда застревал в `PENDING`, а
  реконсиляция перезапускалась бесконечно.
* `white_ads.list` содержал домены, а сравнивался с именами пакетов —
  файл был мёртвыми данными.
* RESCAN из Action-меню не перезапускал индексатор, то есть не обновлял
  единственный работавший слой.
* «Safety freeze» на 15 совпадениях глушил PM-слой даже при явном включении.
* `dumpsys package packages` выполнялся безусловно при каждой инвентаризации.
* Мёртвая функция писала ошибку в лог при каждой загрузке.

Подробный разбор: `reports/AAD_v6.2.0_AUDIT.md`.

### Обновление с v6

Установщик останавливает процессы старой версии, возвращает в исходное
состояние компоненты, отключённые через PackageManager, снимает цепочки
`iptables` `AAD_ADKILL` и удаляет кэши. Логи и настройки сохраняются.

Если часть компонентов вернуть не удалось, состояние сохраняется и попытка
повторяется при следующей установке или при удалении модуля.

### Исправлено по итогам проверки на устройстве

Проверено на OnePlus PJA110, Android 16 (API 36), KernelSU 3.3.0 + ReZygisk.

* **Zygisk определялся неверно.** Установщик искал только модуль `zygisksu`
  и на ReZygisk сообщал «Zygisk не обнаружен», хотя тот работал. Проверка «в
  имени есть zygisk» тоже негодна — под неё подпадает LSPosed. Теперь ищутся
  оба провайдера по идентификатору и их рабочие каталоги.
* **Firebase Analytics не выключался.** Метод `setAnalyticsCollectionEnabled`
  в собранном приложении отсутствовал: R8 вырезает его, если само приложение
  сбор не выключает. Добавлен поиск метода по нескольким сигнатурам, а если
  метода нет вовсе — флаг пишется прямо в настройки SDK
  (`com.google.android.gms.measurement.prefs`), откуда тот его и читает.
* **Движок лез в app-zygote.** Chromium-браузеры форкают детей из процесса
  `<пакет>_zygote`, где нет пригодной среды Java: загрузчик впустую поднимал
  поток и получал ошибку `AttachCurrentThread`. Такие процессы исключены.
* **Мусор в выводе установщика.** Сообщение оболочки об убитом по таймауту
  `getevent` попадало в лог установки как `Terminated`.
* **Повторная установка стирала пользовательские правила.** Очистка наследия
  v6 удаляла `rules.conf` — в v6 это был генерируемый файл, в v7 под тем же
  именем лежат правила пользователя. Блок стал одноразовым, под маркером.

### Требования

Zygisk обязателен: Magisk с включённым Zygisk, KernelSU + ZygiskNext или APatch.
Без него модуль не активируется, установщик предупреждает об этом.
