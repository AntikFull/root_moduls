# Analytics & Ads Disabler v7.0.1

Root-модуль для Magisk / KernelSU / KernelSU Next / APatch, блокирующий рекламу
и аналитику **внутри процессов приложений**, без списков доменов в основе
и без сканирования APK.

Автор: `eCubz` (https://t.me/eCubz)
Группа поддержки: https://t.me/module_ecubz

---

## Чем v7 отличается от v6

v6 работала снаружи: сканировала APK всех приложений, искала рекламные SDK в
DEX-файлах и строила по результатам правила `iptables`. Это давало часы работы
процессора при установке, десятки гигабайт чтения-записи и почти нулевой эффект:
правила по `-m string` требуют модуль ядра `xt_string`, которого в прошивках
обычно нет, и не покрывают QUIC.

v7 заходит с другой стороны. Zygisk загружает движок в процесс приложения, и
дальше блокировка делается изнутри — там, где рекламный SDK уже виден по именам
классов и где его сетевые вызовы проходят через `ProxySelector`.

| | v6.2.0 | v7.0.1 |
|---|---|---|
| Объём shell-кода | 12 312 строк | 1 004 строки |
| Постоянных фоновых процессов | до 5 | 1 (`inotifyd`, спит в ядре) |
| Опрос состояния | каждые 10 с, плюс `iptables` из цикла | нет |
| Сканирование APK | все `classes*.dex` каждого приложения | нет |
| Нагрузка в простое | заметная | отсутствует |

## Как это работает

### Слой 1. Сетевой перехват внутри процесса

Движок подменяет `ProxySelector` приложения. Все клиенты поверх `java.net` —
`HttpURLConnection`, OkHttp, Retrofit, Volley — спрашивают у него маршрут перед
каждым соединением. Рекламный запрос получает заведомо мёртвый прокси на
`127.0.0.1:1` и мгновенно завершается отказом.

Запрос отклоняется, если выполнено одно из условий:

1. хост входит в список рекламных эндпоинтов (~110 записей) или эндпоинтов
   аналитики (~29 записей);
2. **соединение открывает код рекламного SDK или трекера** — движок смотрит
   стек вызовов и ищет в нём кадры из `com.google.android.gms.ads.`,
   `com.applovin.`, `com.unity3d.ads.`, `com.appsflyer.`, `com.adjust.sdk.`,
   `com.google.android.gms.measurement.` и подобных.

Второе условие и есть ответ на «не хочу следить за списками». Имена пакетов
публичного API рекламных сетей и трекеров — это версионируемый контракт,
который они не могут ломать: на нём завязаны все приложения.
`com.google.android.gms.ads.AdView` существует с 2014 года. Домены же меняются
постоянно.

Оба переключателя — `BLOCK_ADS` и `BLOCK_ANALYTICS` — работают по одной и той
же схеме, каждый со своим набором сигнатур. Реклама имеет приоритет при
распознавании: рекламные SDK тянут за собой собственную измерительную обвязку,
и относить такой вызов к аналитике неверно.

Отдельно защищена общая инфраструктура (`googleapis.com`, `gstatic.com`,
`facebook.com`, CDN): по стеку вызовов она не блокируется никогда, иначе
рекламный код, обратившийся к Firebase, или сбор App Events, идущий на тот же
`graph.facebook.com`, что и вход по Facebook, утащили бы за собой рабочие
функции приложения. На явные списки эта защита не распространяется —
рекламный `an.facebook.com` блокируется как и раньше.

### Слой 0. Штатное выключение SDK

Работает раньше всех остальных и стоит дешевле всех.

У систем аналитики есть собственный выключатель, сделанный ради GDPR:
`FirebaseAnalytics.setAnalyticsCollectionEnabled(false)`, `AppsFlyerLib.stop()`,
`Adjust.setEnabled(false)`, `AppMetrica.setDataSendingEnabled(false)` и другие.
Движок вызывает их через рефлексию при запуске приложения.

Разница с блокировкой сокета существенная. При сетевой блокировке SDK
продолжает работать: собирает события, пишет их на диск, батчит, отправляет,
получает отказ и ставит повторную отправку с нарастающей паузой. Штатный
выключатель гасит сбор в самом SDK — не остаётся ни событий, ни записи на
диск, ни ретраев, ни попыток соединения.

Это не обход, а предусмотренный вендором режим, поэтому риск сломать
приложение минимален. Отсутствие класса означает, что этого SDK в приложении
просто нет, и обрабатывается как обычный случай.

Поддержаны: Firebase Analytics, Google Analytics, AppsFlyer, Adjust,
AppMetrica и Yandex Metrica, Amplitude, Branch, Facebook App Events, Countly.
Остальное закрывается сетевым слоем.

У рекламных SDK равнозначного API нет по понятной причине — вендор его не
поставит. Реклама гасится слоями 1–4.

### Что считается аналитикой

Блокируется то, что собирает данные и ничего не даёт пользователю взамен:
Firebase Analytics, Google Analytics, AppsFlyer, Adjust, AppMetrica, Amplitude,
Mixpanel, Branch, Kochava, Singular, Segment, CleverTap, Flurry, Countly,
mParticle, Facebook App Events, а также системы записи пользовательских сессий
(Smartlook, FullStory, UXCam, Contentsquare).

Намеренно **не** блокируется:

* push и in-app сообщения (OneSignal, Braze, Leanplum, Localytics, Pushwoosh) —
  их блокировка выглядит как пропавшие уведомления;
* диагностика сбоев (Crashlytics, Sentry) — она не следит за пользователем
  между приложениями;
* Firebase Remote Config и Installations — от них зависит работа приложения.

Почему отказ, а не «чёрная дыра»: SDK получает обычную сетевую ошибку и штатно
сообщает приложению «нет заполнения». Приложение не висит в таймауте, не копит
повторы и не показывает экран «обнаружен блокировщик».

### Слой 2. Схлопывание контейнеров

Заблокированный баннер оставляет на экране пустую полосу — место под него уже
размечено. Движок обходит дерево View и схлопывает рекламные контейнеры
(`AdView`, `MaxAdView`, `BannerAdView` и т. д.), а вместе с ними — опустевшие
обёртки, но не более трёх уровней вверх и никогда до корня экрана.

Обход ограничен по глубине и по числу узлов, повторные проходы по сигналу
`layout` разрежены во времени. Вердикты по именам классов кэшируются, поэтому
почти всё сопоставление сводится к чтению из хеш-таблицы.

### Слой 3. Полноэкранные экраны

Interstitial, app-open и rewarded показываются как Activity рекламного SDK.
Движок закрывает их в `onActivityCreated`, до отрисовки.

### Слой 4. Косметика в WebView

Во встроенных браузерах приложений внедряется CSS, скрывающий стандартные
рекламные блоки (`ins.adsbygoogle`, `div[id^='div-gpt-ad']` и т. п.).

## Чего модуль не делает

Об этом лучше знать заранее, чем считать багом.

* **Реклама на сайтах в браузерах не блокируется.** Это касается Chrome, Edge,
  Firefox, Opera и любого другого самостоятельного браузера.

  Движок в браузер попадает — он не исключён и запускается в его процессе.
  Толку от этого нет: браузер грузит страницы **собственным нативным сетевым
  стеком** (у Chromium — Cronet), который про `ProxySelector` из мира Java не
  знает вообще. Косметический фильтр тоже неприменим: свой рендерер, а не
  системный WebView. Проверено на устройстве — движок в процессе есть,
  отклонённых запросов ноль.

  Обойти это рут-методами нельзя: понадобилось бы патчить сам браузер.
  Что реально работает:
  * встроенный блокировщик самого браузера — он есть у Edge, Opera, Brave,
    Kiwi; включается в настройках браузера;
  * Firefox с расширением uBlock Origin;
  * фильтрация на сетевом уровне вне процесса — DNS-синкхол или SNI-фильтр
    (например `nfqws2`). Запросы режет, но оставляет дыры в вёрстке и требует
    списка доменов.

  Реклама **внутри приложений** и во встроенных в приложения браузерах
  (WebView) блокируется — это разные каналы.
* **Cronet идёт мимо `ProxySelector`.** Часть приложений использует нативный
  сетевой стек Google. Там работают слои 2–4, но не слой 1.
* **Реклама, встроенная в собственный контент приложения**, не распознаётся:
  для движка это обычные элементы интерфейса.
* **Компоненты через PackageManager больше не отключаются.** Этот слой был
  выключен по умолчанию ещё в v6.1.9 из-за поломок приложений и в v7 удалён.
  При обновлении всё, что v6 успела отключить, возвращается в исходное состояние.

## Требования

* Zygisk: Magisk с включённым Zygisk, либо KernelSU + ZygiskNext, либо APatch.
* Android 8.0 (API 26) и новее.

Без Zygisk модуль не работает: устанавливать его в этом случае бессмысленно,
установщик об этом предупредит.

## Настройка

Файл `/data/adb/analytics_ads_disabler/settings.conf`:

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `BLOCK_ADS` | 1 | Блокировать рекламу |
| `BLOCK_ANALYTICS` | 1 | Блокировать аналитику и атрибуцию |
| `INCLUDE_SYSTEM_APPS` | 0 | Обрабатывать системные приложения |
| `NET_GUARD` | 1 | Сетевой слой |
| `SDK_OPT_OUT` | 1 | Выключать аналитику её штатным API |
| `COLLAPSE_VIEWS` | 1 | Схлопывание контейнеров |
| `CLOSE_AD_SCREENS` | 1 | Закрытие полноэкранной рекламы |
| `WEBVIEW_COSMETIC` | 1 | Косметика в WebView |
| `AUDIT_LOG` | 0 | Режим разбора: логирует каждый хост с вердиктом |
| `VERBOSE_LOG` | 0 | Подробный лог в logcat, тег `AAD-Core` |

Изменения подхватываются автоматически (`inotifyd`) либо по кнопке **Action**
в менеджере root. Применяются при следующем запуске приложения — уже запущенные
нужно закрыть из списка недавних.

`whitelist.list` — приложения, в которые движок не внедряется совсем. По
умолчанию туда внесены банковские приложения: внедрение постороннего кода в их
процесс может привести к отказу в обслуживании со стороны самого приложения.

### Свои правила

`rules.conf` — собственные сигнатуры, если встроенных не хватило. Секции:

| Секция | Что добавляет |
|---|---|
| `[AD_PACKAGES]` | Префикс пакета рекламного SDK |
| `[ANALYTICS_PACKAGES]` | Префикс пакета трекера |
| `[AD_HOSTS]` | Рекламный эндпоинт |
| `[ANALYTICS_HOSTS]` | Эндпоинт аналитики |
| `[NEVER_BLOCK_HOSTS]` | Хост, который нельзя блокировать по выводу из стека |
| `[AD_VIEWS]` | Класс рекламного контейнера для схлопывания |
| `[AD_ACTIVITIES]` | Класс полноэкранного рекламного экрана |

Правила **добавляются** к встроенным; убрать встроенную сигнатуру через этот
файл нельзя — так правило не может случайно снять защиту. Если конкретное
приложение ломается, исключите его целиком в `whitelist.list`.

Хосты сопоставляются по домену и всем поддоменам: `ads.example.com`
перекрывает и `eu.ads.example.com`. Не указывайте общий домен продукта —
`example.com` отрежет приложению и его собственный API.

Секция `[NEVER_BLOCK_HOSTS]` нужна, если после установки приложение перестало
грузить свой контент: значит, эвристика по стеку задела рабочий хост. На
явные списки эта защита не действует, явное правило всегда сильнее.

Системные процессы, сервисы Google, магазины, клавиатуры, WebView и менеджеры
root исключены на уровне движка, перечислять их не нужно.

### Если приложение сломалось

1. Добавьте его в `whitelist.list`.
2. Если реклама нужна ради награды — выключите `CLOSE_AD_SCREENS`.
3. Если приложение не грузит контент — выключите `NET_GUARD` и сообщите,
   какое именно: значит, эвристика по стеку задела рабочий хост.

## Если реклама всё равно показывается

Так бывает: рекламные SDK часто перепакованы обфускатором, и сигнатура по
имени пакета их не видит. Для таких случаев есть режим аудита — он показывает
не только заблокированное, но и **пропущенное**.

1. Поставьте `AUDIT_LOG=1` в `settings.conf`.
2. Перезапустите приложение (закройте из списка недавних).
3. Соберите лог:

```
logcat -s AAD-Core | grep AUDIT
```

Вывод состоит из двух частей.

**Какие SDK нашлись в приложении:**

```
AUDIT SDK в com.example.app | реклама: AppLovin MAX, myTarget | аналитика: Adjust
```

**Вердикт по каждому хосту с указанием, чей код открыл соединение:**

```
AUDIT БЛОК    ad.mail.ru инициатор=реклама:com.my.target.c5
AUDIT ПРОПУСК yandex.ru инициатор=реклама:yads.u2
AUDIT ПРОПУСК api.example.com инициатор=прочее:n51.i
```

Строка `ПРОПУСК` с инициатором `реклама:` — это утечка. Префикс пакета из неё
(здесь `yads.`) добавляется в секцию `[AD_PACKAGES]` файла `rules.conf`.

Строка `ПРОПУСК` с инициатором `прочее:` — обычный трафик приложения, трогать
не нужно.

Именно так в v7.0.1 была найдена перепакованная Яндекс.Реклама: имя класса в
каждой сборке своё (`yads.zq2`, `yads.u2`), поэтому ловить её можно только по
префиксу пакета.

Аудит заметно нагружает лог, поэтому в обычной работе держите его выключенным.

## Диагностика

```
logcat -s AAD-Engine AAD-Core
```

`AAD-Engine` — нативный загрузчик (решение о внедрении), `AAD-Core` — Java-ядро
(блокировки). Подробности включаются `VERBOSE_LOG=1`.

Логи shell-слоя: `/data/adb/analytics_ads_disabler/logs/`.

Файл политики `engine.policy` показывает, что именно видит движок:
строка `F|` — флаги, строки `X|` — исключённые пакеты.

## Обновление с v6

Установщик сам:

1. останавливает фоновые процессы v6;
2. возвращает в исходное состояние все компоненты, отключённые через
   PackageManager (используется механизм отката самой v6 — он сверяет текущее
   состояние компонента с тем, что применял модуль, и не трогает изменённое
   пользователем);
3. снимает цепочки `iptables` `AAD_ADKILL`;
4. удаляет кэши старого движка, сохраняя логи и настройки.

Если часть компонентов вернуть не удалось, `component_state.list` сохраняется,
и попытка повторяется при следующей установке или при удалении модуля.
